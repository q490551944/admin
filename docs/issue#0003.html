Issue #3 — 搭建聊天模块基础设施与数据库迁移 — 2026-08-19

Design Decisions

Decision 使用单一会话表承载公共房间与一对一私聊

Ambiguity: SPEC 给出了两类会话及各自唯一键，但没有规定应拆表还是共用表。

Choice: 通过 type 区分 PUBLIC_ROOM 与 DIRECT_MESSAGE，并使用形态检查约束确保只有对应类型的字段可被填写。

Rationale: 共用 ID 空间和最近消息字段可以简化后续会话列表、消息关联与统一鉴权，同时数据库约束能防止不完整状态进入系统。

Decision 将并发不变量下沉到数据库唯一约束

Ambiguity: Issue 要求房间名、私聊和消息请求保持唯一，但未指定仅由服务层判断还是由数据库兜底。

Choice: 为归一化房间名、私聊 direct_key、参与者关系、附件对象名和 (sender_id, client_request_id) 创建唯一约束。

Rationale: 服务层的先查后写无法独立阻止并发竞态，数据库约束是所有写入路径共享的最终一致性边界。

Decision 默认关闭聊天功能并通过环境变量提供存储凭据

Ambiguity: SPEC 建议分阶段发布，但没有给出特性开关默认值和凭据配置方式。

Choice: chat.enabled 默认设为 false，Service 实现仅在开关启用时注册；MinIO 端点、桶和凭据通过 CHAT_ATTACHMENT_* 环境变量覆盖。

Rationale: 后续接口尚未完成时不会意外暴露半成品功能，同时避免把真实密钥提交到仓库。

Deviations

Deviation 迁移集成测试使用 H2 MySQL 模式

Spec: SPEC 第 14 节提出使用 MySQL 验证数据库约束。

Implementation: 自动化测试使用内存 H2，并启用 MODE=MySQL；生产依赖和运行配置仍使用 MySQL 与 flyway-mysql。

Reason: 当前仓库没有可复用的容器化 MySQL 测试设施。H2 可以稳定验证空库迁移、重复执行和关键唯一约束，但正式发布前仍需在目标 MySQL 版本上做一次迁移演练。

Tradeoffs

Tradeoff 数据库默认值与应用层自动填充

Alternatives: 可以完全依赖 MyBatis-Plus 的时间字段填充，也可以由数据库为创建时间和状态提供默认值。

Choice: 迁移脚本为创建时间、版本和初始状态定义数据库默认值，实体保留相应字段供后续业务读取和更新。

Why: 数据库默认值能够覆盖批处理或未来非 ORM 写入路径；代价是后续更新 updated_at 时仍需服务层或 MyBatis 填充器明确维护。

Tradeoff 当前只交付 Service CRUD 骨架

Alternatives: 可以在基础设施 Issue 中同时实现房间、消息和附件业务规则，或将其保留给后续独立 Issues。

Choice: 本次只建立实体、Mapper、条件化 Service 实现和持久化约束。

Why: 保持 Issue #3 独立可交付，并避免提前固化 #4–#11 的鉴权、事务和状态机设计；代价是开启特性开关本身不会产生可用的聊天 API。
